SharpAgent technical design

A practical build blueprint for a web-based AI coding agent: a modern React experience over a .NET service that applies policy, preserves an audit trail, isolates coding work, and uses Microsoft Agent Framework behind a stable application boundary.

Version: 1.0 Date: 23 August 2026 Audience: Delivery team, technical sponsors, coding agents Companion: Implementation Markdown

Recommended implementation decision

Build the controlled MVP as one bounded service, not as a free-form autonomous agent

The design uses Microsoft Agent Framework for long-running agent behavior, while SharpAgent itself controls every consequential action. The result preserves the useful coding-agent experience shown in the prototype without allowing a browser or model to bypass the application’s guardrails.

What the delivery team builds

A React web application provides the conversation-first workspace, approvals, change review, dashboards, settings, themes, and tablet-responsive experience. A .NET 10 backend persists durable session facts in SQLite, streams updates over SSE, routes models through adapters, and runs controlled work in an isolated environment.

The core decision is deliberate: MAF is the agent engine, while SharpAgent retains product ownership of policy, fingerprints, workspace validation, cancellation, audit records, and recovery.

Important boundary

MAF is deliberately hidden behind an application interface. This allows the team to adopt the Harness capabilities that prove reliable without making UI, persistence, policy, or provider decisions dependent on a framework detail.

Controlled execution loop

The agent can propose work; only the application can authorize and perform it

The interaction looks conversational to the developer, but every consequential action follows a durable decision path.

01

Start a session

The developer chooses a registered workspace, validated model profile, mode and tighter limits where needed.

02

Plan and inspect

The Harness produces visible todos and can use approved in-boundary read/search actions.

03

Evaluate proposal

SharpAgent evaluates a normalized patch or command against policy, boundaries and run limits.

04

Approve once

Sensitive work pauses until an operator approves, denies or cancels one exact fingerprinted action.

05

Review evidence

Bounded output, diffs, validation results, usage, outcome and next step are retained for review.

Trust and safety design

The browser can request work, but cannot reach the repository or providers directly

The design converts the prototype’s visible approval and recovery controls into enforceable server-side rules. It is intended to make unsafe behavior difficult by construction, not merely inconvenient in the UI.

Browser-side responsibility

Render tasks, plans, streaming activity, approval previews, diffs, terminal summaries, dashboard metrics, settings and recovery choices. Send typed commands with an idempotency key.

Never: secrets, raw shell, filesystem, direct provider calls

Server-side responsibility

Validate paths and profiles, control the run lifecycle, calculate fingerprints, persist audit facts, execute bounded tools, resolve secrets, normalize providers and emit safe SSE events.

Owns: policy, approvals, workspace, persistence, recovery
Action categoryDefault decisionWhat makes it safe
Read/list/search inside workspaceAllowCanonical path validation, boundary check, bounded output.
Patch or write fileApprove onceNamed change set, affected paths, deterministic fingerprint, isolated worktree.
Focused test or shell commandApprove onceStructured executable/arguments, worktree-only directory, timeout and output cap.
Delete, install, publish, commit or pushDenyNot part of the controlled MVP command catalog.
Network access from a workspace toolDenyOutbound network disabled by default; provider adapters are separate server-side paths.

Approval is an enforceable permit

Every approval is tied to a specific run, action type, resolved paths, patch or command contents, execution environment and policy version. The server re-checks the fingerprint and expiry immediately before execution.

  • Single use and active-run scoped
  • Expires using server time
  • Cannot be replayed after a changed patch or command
  • Cancellation invalidates pending approvals

Isolation is not optional

Command allowlists alone are not a sandbox. Slice 0 chooses and proves an isolated environment, preferably a disposable Git worktree; a least-privilege, network-disabled container is the alternative.

  • Original checkout is treated as a read-only baseline
  • Agent patch is retained as reviewable diff evidence
  • Process tree, time and output are bounded
  • Traversal and escaping symbolic links are denied before action

Durable session and event design

SQLite stores the facts that let a session survive refresh, interruption, and resume

The live stream never becomes the system of record. The service commits state and an ordered audit event first; SSE subscribers receive those committed facts second.

SessionTask, workspace, mode, selected profile, archive state and active run reference.
Agent runOne attempt, sequence, execution environment, context summary, stop reason and final summary.
Audit eventAppend-only ordered record of status, policy, approvals, tools, changes and outcome.
Approval requestImmutable preview, fingerprint, expiry, decision and consumption status.
Change setFiles, hashes, bounded diffs and testable review evidence for a run worktree.
Usage recordProvider, model profile, token/cost data when supplied, latency and compaction count.

Recovery by reconstruction

The implementation does not serialize framework session objects as long-term product data. On resume it creates a new run and a new MAF session from the persisted task, compacted context, todos, approvals, changes and safe summaries. Previous runs stay immutable.

Event ruleImplementation outcome
OrderedEvery session event receives a monotonic sequence. The stream ID is the durable sequence.
ReplayableReconnect uses Last-Event-ID. A gap causes a session projection refresh before reconnect.
SafeEvents expose concise intent, scope, result and error summaries; never hidden reasoning, keys, raw provider payloads or unrestricted environment values.
Idempotent commandsState-changing requests require a key; retries return the original outcome or a conflict, not duplicate work.
Bounded concurrencyA transactional run lease prevents more than one active run per session in the one-service MVP.

React web experience

The production UI preserves the prototype’s coding-agent feel while making server state authoritative

The visual reference is a browser application with a conversation-first agent workspace, not a desktop clone. It uses React Router, shadcn/ui components, Tailwind CSS 4 and strict TypeScript.

/sessions/:id/changesFocused diff and changed-file review
/sessions/archiveArchived sessions retained for review and restoration

Visible behavior carried forward

  • Plan/Execute mode and visible todos
  • Patch and focused-test approvals with expiry and fingerprint metadata
  • Cancel, archive and resume with optional follow-up
  • Context-compaction, provider-error, limit and stream-interruption states
  • Diff, terminal, activity and final-review views
  • Dashboard, statistics, administration and four persistent themes

Key production differences from the prototype

  • All session facts come from typed API projections and SSE events.
  • Local storage holds only theme and non-sensitive layout preferences.
  • Buttons display pending state but await server confirmation for safety/outcome changes.
  • Model validation and execution eligibility are server decisions, never UI-only logic.
  • Responsive details/navigation become accessible sheets at tablet widths.

Delivery gates and quality

Deliver in proof-oriented slices, with the hardest safety assumptions verified first

The plan avoids building a polished interface on unproven agent, provider or workspace behavior. Each slice has an explicit exit test.

0

Technical validation

Prove the isolated workspace mechanism, all requested provider adapters, MAF Plan mode/todos, SSE, SQLite audit events, read/search tools, health and usage.

Exit: a validated profile plans a real repository task and survives refresh with no side effect.
1

Controlled MVP

Deliver the React routes, Execute mode, policy/approval service, patch/test flows, replay, cancellation, archive/resume, diff/review, reporting and settings.

Exit: a trusted developer completes a small isolated-worktree change with approval and validation evidence.
2

Pilot hardening

Improve isolation and degraded-provider behavior, add operational metrics/retention, document deployment/backup, and evaluate optional explicit fallback.

Exit: pilot evidence supports decisions on wider use, authentication and a future server database.
