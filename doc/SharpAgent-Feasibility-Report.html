Management feasibility report

SharpAgent

Feasibility assessment for a controlled AI coding-agent platform built on React, .NET 10, Microsoft Agent Framework, SQLite, and a flexible model-provider layer.

Decision: Proceed with a controlled MVP Report date: 23 August 2026 Audience: Management and delivery sponsors
Decision Stack fit Architecture Delivery plan Risks Sources

Executive conclusion

Feasible, with a clear boundary between the agent runtime and the product we must build

SharpAgent can deliver the practical capabilities of a modern coding agent: understanding a repository, planning work, editing files, running tests, asking before sensitive actions, and streaming progress to the user. Microsoft Agent Framework provides the core agent runtime; the SharpAgent team would build the user experience, workspace controls, provider integration, and operational safeguards around it.

Recommended decision

Fund a controlled MVP rather than a full product-parity programme. The MVP should prove three things early: selected models can reliably stream and call tools; workspace actions can be contained and approved; and users gain measurable value on real development tasks.

Overall feasibility Proceed High for a local or trusted internal pilot; conditional for shared deployment.

What is already available

MAF supplies multi-step tool use, planning and todos, sessions, context management, approvals, streaming, and observability foundations.

What SharpAgent adds

A polished React experience, Git-aware workspace tools, safe file changes, provider routing, human approval flows, and delivery operations.

What needs discipline

Shell access and external model providers are powerful but not inherently safe. Isolation, policy, cost limits, and staged rollout are mandatory.

Architecture principle: treat Microsoft Agent Framework as the orchestration engine, and place model providers behind a small capability-aware adapter. This avoids locking the product to a specific provider or model contract.

Target architecture

A simple control plane around an isolated coding workspace

The browser never receives provider keys or direct shell access. The .NET backend owns sessions, policy enforcement, and model requests. SQLite stores MVP state; a disposable worktree or isolated container performs coding actions.

Operating model

The agent is autonomous within defined boundaries, not unattended

The Harness coordinates model and tool calls, but SharpAgent controls what the tools are allowed to do. Users remain in the loop for actions with material consequences.

Model-provider strategy

Support all three providers, but treat capability as a testable contract

The integration is feasible because each provider offers accessible API surfaces. The practical constraint is not connecting to a model; it is ensuring that the selected model reliably supports the features a coding agent needs: streaming, structured tool calls, sufficient context, predictable latency, and acceptable data handling.

ProviderIntegration approachStrength in SharpAgentDecision / caution
OpenCode Go Provider-specific adapter. Its catalog uses different endpoint styles for different models: OpenAI Responses, Chat Completions, and Anthropic Messages. Cost-conscious, curated coding-model access. Do not assume one universal API shape or permanent model catalog. Validate the selected model and endpoint before enabling it for autonomous tools.
DeepSeek OpenAI/Anthropic-compatible API adapter, with provider-specific settings held server-side. Direct model access and a documented compatible API surface. Validate tool calling, reasoning mode, rate limits, and data policy on the intended models during Phase 0.
OpenRouter OpenAI-like Chat Completions adapter with model capability registry and explicit fallback rules. Broad model choice and resilience through routing options. Tool support varies by upstream model/provider. Only allow the agent loop to use models that pass our integration test suite.

Recommended provider contract

Expose a small internal interface for model catalog, streaming response, tool calls, token usage, capability flags, and error normalization. The rest of the product should not know which external provider served the task.

Recommended initial routing

Choose a small approved model set rather than a free-for-all picker. Use one primary model for coding tasks, one lower-cost model for simple work, and one fallback after reliability has been proven.

Provider API keys must remain server-side. With authentication out of scope, the MVP should use a trusted deployment model and locally managed secrets rather than expose credentials through the browser or SQLite.

Delivery plan

Stage investment so the important risks are proven before scale

Phase 0 — Validate

Build only enough to test the provider adapter, streaming, tool calls, SQLite persistence, and a controlled read-only workspace.

Phase 1 — MVP

Deliver the complete user journey: task, plan, approval, edit, test, review, and resume a session.

Phase 2–3 — Learn then scale

Use pilot evidence to prioritize hardening, support, broader repositories, and any future authentication or central-database decision.

Risks and controls

The major risks are controllable, but they should shape the delivery order

Risk
Why it matters
Recommended control
Unsafe workspace action
A model can propose commands or edits with unintended side effects.
Disposable worktrees or containers, narrow path scope, timeouts, explicit approvals, and no direct browser-to-shell path.
Model inconsistency
Tool calling and quality can vary across providers and even models in the same catalog.
Capability registry, contract tests, approved model list, and a fallback provider. Never make a model broadly available solely because it appears in a picker.
Cost variability
Long-running tool loops and large repository context can make costs unpredictable.
Per-session budget, context limits, telemetry, model routing, and an explicit stop condition.
No authentication
There is no durable identity boundary for a shared service, provider key ownership, or audit accountability.
Launch the MVP only locally or in a tightly trusted setting. Add authentication and authorization before shared or Internet-facing use.
SQLite concurrency
SQLite is ideal for the local MVP but becomes a constraint when many concurrent users or workers share one service.
Use EF Core repository boundaries and migrations. Reassess a server database only when the pilot proves a shared deployment is needed.
Framework feature maturity
MAF’s core is production-oriented, but some coding-adjacent features are still evolving.
Pin tested versions, isolate framework calls behind application interfaces, and exercise the actual shell/file pattern during Phase 0.
Release boundary: do not expose SharpAgent publicly or to untrusted networks without authentication, user isolation, durable audit ownership, and a reviewed secret-management design.

Pilot success criteria

Measure value, not just model output

Useful completion

Task outcomes are judged by reviewed diffs, successful builds/tests, and developer acceptance—not by the fluency of the response.

Operational confidence

Track tool failures, approval requests, cancelled runs, provider errors, latency, and recoverable session resumes.

Cost discipline

Track cost per completed task, token use, context size, and provider/model selection so the business can compare value against spend.
