A practical, guarded AI coding-agent experience for trusted developers: plan work, act inside an isolated workspace, and keep people in control of consequential changes.

The product in one view

Turn a development task into a visible, controlled workflow

SharpAgent is not an unattended coding bot. It is a developer-facing workspace where the agent can understand a repository, prepare a plan, propose a change, run validation, and explain the outcome—while the application controls file access, shell execution, model choice, and approval.

01

What a developer gets

A single place to create coding tasks, see live progress, inspect a todo plan, review diffs, and continue a session later.

02

What the agent does

Uses Microsoft Agent Framework to plan, manage task context, call approved tools, and stream useful status—not hidden model reasoning.

03

What keeps it safe

Every potentially consequential tool action passes through application policy, a bounded workspace, and an approval decision where required.

!
MVP deployment boundary

Authentication is deliberately not included. This version is for a local machine or tightly trusted internal use only. A shared or Internet-facing deployment is blocked until authentication and authorization exist.

Plan mode — investigate before acting

Use this mode for repository understanding, root-cause analysis, task decomposition, and a proposed path forward.

  • Can read, list, search, and inspect repository state inside the selected workspace.
  • Creates and updates a visible todo plan.
  • Never patches files or runs a side-effecting shell command.
Execute mode — act only inside guardrails

Use this mode for a small, reviewable change that can be validated inside the controlled workspace.

  • Begins with a plan and tracks progress through todos.
  • Requests approval before default-sensitive actions such as patches and test commands.
  • Finishes with a change review, validation result, warnings, and usage summary.

Functional scope

Capabilities that make the MVP useful

The functions below are the committed behaviour for the first usable product. They are intentionally focused on an auditable developer workflow rather than broad, unattended autonomy.

A

Tasks and sessions

  • Create a task with a workspace, model profile, and Plan or Execute mode.
  • List recent sessions and see state, workspace, model, and outcome.
  • Cancel, archive, and resume sessions without losing history.
B

Planning and context

  • Visible todos for multi-step work.
  • Compaction of long-running context while preserving key decisions.
  • Clear activity summaries rather than private model reasoning.
C

Changes and validation

  • Proposed patches grouped as change sets.
  • File-by-file diff review.
  • Controlled test and shell execution with output and exit status.
D

Safety and approval

  • Policy decision before every tool action.
  • Single-use, expiring approvals for sensitive work.
  • Hard workspace boundary and isolated execution profile.
E

Model choice

  • Server-side adapters for OpenCode Go, DeepSeek, and OpenRouter.
  • Small approved catalog instead of unrestricted model pickers.
  • Profile validation for streaming and tool calling.
F

Results and learning

  • Final summary, completed todos, changed files, and next steps.
  • Audit timeline across task, tools, policy, approvals, and outcome.
  • Usage, latency, tool count, and estimated-cost visibility.

Control model

Autonomous within limits, never unattended

SharpAgent can take several steps in sequence, but it cannot bypass the product boundary. The browser never holds provider keys or has direct shell access; the backend owns the session and evaluates policy before an action reaches files or commands.

Draft→ Planning→ Executing→ Awaiting approval→ Reviewing→ Completed orCancelled / failed / interrupted
ActionDefault decisionWhy it is treated this way
Read, list, search inside workspaceAllowUseful repository understanding with bounded, resolved paths.
Apply a patch or write a fileRequire approvalChanges the developer's working code and must be reviewed.
Run a test or shell commandRequire approvalMay consume resources or have unexpected side effects.
Delete, move, install, publish, commit, or pushDeny in MVPOutside the initial safe operational envelope.
Access outside workspace or tool network accessDenyProtects local data and keeps execution scope explicit.

What an approval shows

An approval card names the proposed action, affected files or working directory, safely truncated command or patch preview, agent reason, impact badge, and expiry time.

What an approval never does

Approval is not a blanket permission. It is single-use, linked to one specific action fingerprint, and invalid if the command or patch changes.

Technology and operational behaviour

One application boundary owns the risk

The front end does not connect directly to a model provider or shell. The .NET service owns the persistent session, provider adapter, policy decision, workspace execution, and real-time event stream.

Microsoft Agent Framework

Provides the agent runtime for planning, todo handling, context/session management, streaming, and tool orchestration. SharpAgent wraps it in an application runtime boundary so framework evolution does not leak through the product.

Provider-neutral model layer

OpenCode Go, DeepSeek, and OpenRouter appear to the rest of the system through one canonical contract. Only tested model profiles can run tools.

SQLite and audit history

SQLite stores sessions, plans, approvals, tool records, changes, usage, and configuration metadata. Provider secrets stay in server-side configuration, not the database.

×
Important safety principle

Allow and deny rules are useful but not a sandbox on their own. File and shell actions must be contained by a resolved workspace boundary and an isolated worktree or container profile. Container networking is disabled by default.

MVP acceptance

Evidence required before a controlled pilot

The MVP is complete only when it proves real developer value and the defined safeguards work in practice. The following scenarios form the core acceptance set.

1. Investigate safely

In Plan mode, the agent can read/search a valid repository, create a plan, and return an investigation summary without changing files or running a side-effecting command.

2. Change with approval

In Execute mode, a proposed patch pauses for approval; a separately proposed test command also needs approval; review shows diff and validation result.

3. Deny and recover

A denied or policy-blocked action never runs, is clearly explained, and does not trigger an infinite retry loop.

4. Gate model capability

An unvalidated or incapable provider profile cannot run tool-enabled execution. A passed smoke test makes it eligible according to its capability profile.

5. Resume with history

An interrupted session keeps its task, todos, approvals, tool results, diffs, and failure reason; resuming creates a new run instead of overwriting history.

6. Protect boundary and secrets

Path traversal and escaping symbolic links are denied. No provider credential or raw server secret appears in a page, API result, or browser storage.

✓
Definition of done

All must-have requirements and acceptance scenarios pass; each requested provider has a server-side adapter and validation path; Plan mode is read-only; sensitive Execute actions require approval; history survives refresh/resume; and contract, policy, provider, database, and end-to-end tests run in CI.
